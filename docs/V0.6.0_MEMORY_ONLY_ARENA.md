# v0.6.0：竞技场已选牌改为纯内存 DraftDeck

## 目标与结论

实机发现点击候选查看详情时，游戏会连续写入多条相同的 `Client chooses`（同一张卡 6 次）。日志无法区分“查看”和“选中”，因此日志不能再参与已选牌统计。

本版把数据流收敛为一条：**游戏内存里的当前 `DraftDeck` 就是已选牌的唯一来源**。日志、候选、手写补录、Decks.log 最终定义都不再改变已选牌数量。

## 数据流

```
Hearthstone 进程
   └─ DraftManager.m_draftDeck / m_undergroundDraftDeck
        ├─ ID                    → deck_id（识别同一竞技场）
        ├─ <HeroCardID>          → hero（决定职业评分）
        └─ m_slots[]             → m_cardId + m_count（逐份复制）
              ↓  两次读取一致性校验（原有逻辑，未改动）
        DraftState.deck (tuple)
              ↓  ArenaPreview.feed()：整份替换，不追加
        self.deck
              ↓  view()：按 cost 升序、同费按名称排序
        picks[] / count=len(deck) / count_exact
              ↓
        state.json → 原生 HUD「已选牌 X/30」
```

- 计数：`len(state.deck)`，重复卡按实际份数（同卡 2 份 = 2 行）。
- 排序：`cost` 升序；同费按名称（`name` 字典序，再按 id）；`cost` 缺失的排最后；排序只影响显示顺序，不增删。
- 候选：只来自 `DraftState.choices`，永远不进已选牌区。
- 已选牌不再区分来源，不再有“日志确认/内存历史/顺序未知/重选操作”分区。

## 异常与状态

| 情况 | 行为 |
| --- | --- |
| 同一进程、同一竞技场读取失败（含 `slot_layout`、`no_count_field` 等） | 保留上一份成功快照，`count_exact=false`（面板标“份数待确认”），不回退日志 |
| 进程实例变化 / 游戏退出（`not_running`）/ 关闭内存读取（`disabled`） | 清空快照，不再显示旧牌组 |
| 竞技场 ID 变化 | 先清空再采用新牌组，不混入上一局 |
| 回到英雄选择（`HERO` / `HERO_POWER`） | 视为新一局开始，清空旧牌组 |
| `REDRAFTING` | 以当前内存牌组**替换**，不追加重选事件 |
| 连续读取同一快照 | 每次都是替换，数量不会累加 |

## 移除的代码

- `engine/arena_recovery.py`：日志与内存合并、历史恢复、锚点/窗口、不确定标记，全部删除；`Arena.timed_records()` 随之删除。
- `tests/test_arena_recovery.py`：39 项旧逻辑测试删除，替换为纯内存语义的窗口/新竞技场/读取失败测试。
- `src/arena.tsx`：QAM 里的手动候选录入与补录页面（未在 `src/index.tsx` 中挂载，页面早已移除入口）。
- `scripts/package.py`、`scripts/verify-decky-zip.py`、`tests/test_packaging.py`：移除 `arena_recovery.py` 的必需文件/导入检查。

**未改动**：`engine/arena.py` 的日志解析（`Arena.log` 仍会解析，只是不再影响已选牌）、`Power.log` 普通对局记牌、`Decks.log` 的最终牌组与竞技场对局绑定（`definition_for_game`）、卡牌数据库、评分来源、图片缓存。

## 展示层改动

- `backend/hud_state.h::arena_rows()`：只输出一份平铺列表（已选牌或候选），不再插入任何分区标题。
- `backend/main.cpp`：已选牌面板标题固定为 `已选牌 X/30`，去掉“重选中 · 旧牌组不追加”和“（份数待确认）”前缀。
- 布局、透明度、缩放、触控穿透、分页与滚动逻辑未改动。

## 自动化验证

- `python3 -m unittest discover -s tests`：**185 项通过**（删除 39 项旧恢复测试，新增/改写 14 项纯内存测试）。

- `backend/state_test.cpp` 用 nlohmann/json v3.11.3 在本地编译并运行通过（含 `arena_rows` 平铺断言）。
- 用真实 `state.json` 跑 `valid_hud_state` + `arena_rows` 校验：3 张已选牌（2×0 费 + 1×1 费）排序正确，无 `history_picks`。

覆盖的场景（对应验收清单）：

1. 内存 6 张 → 6/30；2. 同卡 2 次 → 2 行；3. 连续 10 条相同 `Client chooses` → 数量不变（日志模型仍是 10，HUD 仍为 3）；4. 候选不计入；5. 6→7 张替换不追加；6. 费用排序；7. 同费按名称；8. 读取失败保留上一份并标 `count_exact=false`；9. 新竞技场清空；10. 进程重启/退出不显示旧牌组；11. `REDRAFTING` 替换；12. 候选永不混入。

## SteamOS 实机验收

1. 进入竞技场选牌页，确认右侧标题为「已选牌 X/30」，左侧三张候选带评分。
2. 来回点击候选查看详情多次（不选），确认 `X` 不变、列表不增长；复制诊断中 `[Arena] count` 与 `[Arena Memory] deck_parsed` 一致。
3. 实际选一张，确认下一次内存读取后 `X+1`，且该卡出现在费用对应的位置。
4. 选择同一张卡的第二份，确认列表中该卡出现 2 行。
5. 检查排序：逐行费用不递减；同费行按名称排列；`cost` 未知的卡在末尾。
6. 关闭并重开竞技场辅助（同一局），确认牌组保持不变、`count_exact` 恢复为真。
7. 结束本局并开始新的竞技场，确认旧牌组立即消失，新牌组从 0 开始。
8. 完全退出游戏，确认面板消失；重新进入游戏后不显示上一局牌组。
9. 进入地下模式重选，确认列表替换为重选后的当前牌组，不保留旧牌。
10. 完成选牌后进入对局，确认普通记牌面板、双方出牌与剩余牌库功能正常，竞技场面板不干扰对局视图。

## 已知限制

- 内存布局仍限定 Unity 6000.3 x64 / `mono-2.0-bdwgc.dll` / Assembly-CSharp；布局不符时报告不兼容，不猜测。
- 没有内存读取就没有已选牌（不再有日志兜底）。这是本版的明确取舍。
- 内存快照刷新间隔约 500ms，选牌后数量最多延迟一次轮询。
- 本版尚未实机验收；`Snapshot Window` 等旧诊断字段已随恢复模块移除。
