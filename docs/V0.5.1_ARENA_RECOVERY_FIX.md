# v0.5.1：竞技场恢复修复（中途接入 / 时间边界 / 读取隔离）

> 历史版本说明：v0.6.0 已移除日志与内存合并恢复（`ArenaRecovery`），竞技场已选牌改为纯内存 DraftDeck。本文件仅记录 v0.5.1 的行为，见 [v0.6.0 说明](V0.6.0_MEMORY_ONLY_ARENA.md)。

## 实机现象与结论

实机诊断：`Arena ID=3386335194`、`mode=DRAFTING`、3 张候选识别成功、`Association=matched`、`Recovered History=0`、`Recovery=logs`、`Arena count=0`。

`Association=matched` 说明内存牌组 ID 与竞技场 ID 已经一致（否则会显示 `preview_only`），因此问题不在候选识别，也不在 ID 关联，而在“已关联 → 建立快照 → 合并历史”这一段。排查确认了两个真实缺陷，都能单独造成上述现象：

1. **恢复被日志追平状态门控。** `main.py:_arena_view()` 只在 `arena_caught_up or 未发现 Arena.log` 时调用 `ArenaRecovery.observe()`。当中途接入时 Arena.log 未追平、文件陈旧（`discover()` 的 300 秒活跃窗口）或本轮没有新日志写入，`observe()` 根本不会执行，`snapshot` 永远为空，`merge()` 只能返回纯日志结果：`Recovered History=0`、`Recovery=logs`，而此时候选与关联显示完全正常。
2. **内存牌组读取失败是静默的。** `DraftState.deck` 为空（`m_draftDeck` 为空、`m_slots` 为空列表、`m_count` 布局不符或总量越界）时，`observe()` 直接 `return`，不记录原因；旧代码还会在 `m_count` 异常时抛 `UnsupportedLayout`，把整次读取（包括候选）一起丢掉。诊断中也看不到牌组张数、槽位数量或失败原因。

此外修复了合并逻辑中的一个真实错误：`merge()` 判断“待核对记录”时误用了本次循环的局部字典，导致锚点建立之后到达的日志记录被静默丢弃（表现为新选牌不计数）；以及手工补录被日志确认（同轮同卡、`source` 由 `manual` 变 `log`）时 key 变化触发 `log_rewind` 重置、历史牌丢失。

## 对上游结构的核对

`hs-decktracker-linux@649534be99f35cb499ed2fae371625bd04b95b1d` 的 `decktracker/hsmemory.py::draft_state()`：

```python
deck = manager["m_undergroundDraftDeck" if state.underground else "m_draftDeck"]
if deck is not None:
    state.deck_id = str(deck.get("ID") or "")
    state.hero = deck.get("<HeroCardID>k__BackingField") or ""
    slots = deck["m_slots"]
    for slot_obj in slots.list_objects() if slots else []:
        counts = slot_obj["m_count"]      # normal / golden / diamond / ... copies
        state.deck += [slot_obj["m_cardId"]] * sum(counts.list_ints() if counts else [])
```

本地实现与该路径一致：`m_draftDeck` / `m_undergroundDraftDeck` → `ID` + `<HeroCardID>k__BackingField` → `m_slots`（`List<slot>`）→ 每个槽位 `m_cardId` + `m_count`（按版本变体的复制列表，取和）。

因此**没有修改任何字段偏移或类名**，只做了三件事：

- `m_count` 增加“单值 int”容错读取（同一字段的不同布局），并在诊断中标记 `int_count`，不推测其他字段。
- 槽位级异常改为“放弃本次牌组读取并记录原因”，不再让整次内存读取失败（候选识别不受影响）。
- 牌组总量上限 40 份（30 张选牌 + 容错余量）；越界时**不发布任何一张牌**，只报告 `deck_overflow`，不截断、不补齐、不伪造。

### 去重模型（为什么去掉门控仍然安全）

锚点建立时，日志中已确认的记录按复制数量“覆盖”快照副本，其余副本进入“内存历史”。此后：

- 记录时间戳早于锚点 → 是日志迟到投递的历史选择，占用一张仍未被覆盖的快照副本（不新增计数）。
- 记录时间戳晚于锚点且快照已增长 → 用增量信用核对，不重复计数。
- 记录时间戳晚于锚点且快照未增长 → 作为真实新选牌计数（保持原行为，重复 Card ID 按事件计）。
- 锚点使用内存快照的**读取时刻**而非视图刷新时刻，避免“读取之后、渲染之前”的真实选牌被误并入历史。

## SteamOS / Ally X 实机验收步骤

前置：使用包含本修复的构建；竞技场辅助与 Arena 日志均已开启并完全重启炉石。

1. **中途接入基线**：开始一次竞技场，先选 5–10 张，再在 Decky 中关闭并重新开启“竞技场辅助”（或直接启动插件）。进入三卡页后确认：
   - `Association` 为 `matched`，候选 3 张正常显示、评分与推荐不变；
   - `Recovered History` 等于内存牌组张数，HUD 显示 `X/30` 且有“内存历史 · 顺序未知”分组；
   - 复制诊断 `[Arena Recovery]` 中 `Merge Executed: yes`、`Recovery Executed: yes`、`Snapshot: established`、`Snapshot Size` 与 `Memory Deck Size` 一致、`Recovery Reason: recovered`、`Deck Reason: ok`。
   - 若 `Merge Executed: yes` 但 `Recovery Executed: no`，说明合并跑了但没有快照/没有产出，按 `Recovery Reason` 定位（此时不要把它当成“恢复成功”）。
2. **日志滞后场景**：在上一步 `Logs Caught Up: no` 时也应恢复（正是本次修复点）。若 `Recovery Reason` 不是 `recovered`，记录该原因码与 `[Arena Memory]` 的 `deck_object / deck_slots / deck_parsed / deck_reason`：
   - `no_deck` / `no_deck_id` → 内存里没有竞技场牌组对象，属布局/对象状态问题，请附诊断；
   - `deck_empty` 且 `Slot Count > 0` 但 `Memory Deck Size: 0` → 槽位有内容但复制数为 0；
   - `deck_overflow` → 解析出的总量超过 40，属异常读数，不会入账；
   - `deck_unreadable` → 牌组结构无法解析，看 `Deck Reason`（`slot_layout` / `no_slots_field` / `no_count_field` / `slot_without_card_id` 等）；此时三张候选仍应正常；
   - `id_mismatch` → 内存竞技场 ID 与日志不同，未做跨局恢复。
3. **重复卡牌**：选一张已在历史中的同 ID 卡。确认只 +1（不是 +2），且历史分组的同卡份数不变。此时该轮的日志时间应晚于快照时刻，`Pending Cards` 可能出现 1 张，内存下一轮刷新后回到 0。
4. **时间边界**：插件在选牌页停留几分钟后再选一张，确认这张只计一次（日志时间晚于窗口上界 → 独立计数），不会“吃掉”内存历史里的同名牌。`Uncertain Picks` 应为 0、`Snapshot Window` 的时长通常只有几毫秒；非 0 表示有日志落在读取窗口内或缺少时间戳，此时 `count_exact` 显示待确认，等内存下一次刷新会自动收敛。
5. **后续选牌**：连续选 3 张（含 1 张重复 ID），每选一张 `count` 只 +1；等内存下一轮刷新后仍不变。
6. **日志去重**：正常选牌后让日志继续写入若干行，确认不会因为内存历史而重复计数；若日志迟到（延迟数秒），也只补一次。
7. **完成牌组**：选满 30 张后确认 `Decks.log` 的最终定义覆盖恢复结果（`exact`、30/30、历史分组消失），不残留被替换的旧牌。
8. **重选（地下）**：进入重选，确认按新牌组替换而非追加；退出重选回到原牌组时不串场。
9. **回归**：普通对局的记牌、双方出牌面板、候选卡图与评分不变；关闭竞技场辅助后内存线程停止、候选清空、日志记牌继续。

无法从内存/日志取得的信息仍不猜测：内存不可用且日志不完整时不会补出未确认的牌；历史顺序始终标记为未知。

## 后续修正：时间边界、锚点语义与读取隔离

第一轮修复留下三处需要在实机前收紧的地方，本轮逐项修正。

### 1. 快照时间是一个读取窗口，而不是一个点

第一版把时间戳打在 `reader.poll()` 之前（读到的是“开始读”），第二版打在两次一致性读取之后——后者同样有问题：`[第二次牌组读取结束, 打点]` 之间发生的选牌不在牌组里，日志时间却早于锚点，会被当成历史牌吃掉一张快照副本（同 Card ID 还有剩余副本时就是漏计）。

现在 `draft_state()` 记录**读取窗口的两个边界**：

- `snapshot_start`：首个牌组读取**开始之前**写下（此刻之后读到的内容才可能包含该时刻之后的选牌）；
- `snapshot_wall`：牌组复读校验**通过之后立即**写下（此后新选牌必然不在 `cards` 里）。

两者随 `poll()` 的 `observed_start` / `observed_wall` 传给 `MemoryWatch`，`MemoryWatch` 不再自己取时间，只做类型/正值校验，缺失时回退（`observed_start` 缺失 → 用 `observed_wall`，窗口退化为空，等价于旧行为）。时间均为 Unix 时间戳，与 `datetime.timestamp()` 的日志时间可直接比较。牌组对象缺失或结构失败时不产生窗口（两个值都为 0）。

### 2. 锚点、窗口与归属规则

原实现 `anchor=max(observed_wall, 已有日志时间戳)` 会让“快照之后才写下的选牌”把锚点推到它自己的时间上，于是这条日志把快照里原本就有的那张牌“消费”掉，新选牌不计数。

现在 `anchor = observed_start`（窗口下界），另记 `settled = observed_wall`（窗口上界），归属由事件时间决定：

| 日志时间 | 归属 | 计数 |
| --- | --- | --- |
| `ts <= anchor` | 快照已包含的历史选牌（可能只是日志迟到） | 占用一张快照副本，不新增计数 |
| `anchor < ts <= settled` | 落在读取窗口内，无法判定 | 不猜：不占副本、单独计数，标记 `uncertain` |
| `ts > settled` | 快照之后的真实选牌 | 进入 `pending`，独立计数，重复 Card ID 也逐次计 |
| 无可靠时间戳 | 无法判定 | 同窗口内：单独计数 + `uncertain`，`count_exact=false` |

窗口内的记录在判定顺序上优先于“内存增量信用”，避免把一个已经由内存增量证实的后续选牌错配给它；等内存下一次增长真的包含它时，`observe()` 的增量核对会把它转为已覆盖并清除 `uncertain`（不重复计数）。迟到日志按事件本身的时间处理，不按“被读取的时间”处理。

### 3. 牌组解析与候选解析隔离

- 槽位容器（`list_objects`）、槽位字段（`m_cardId`、`m_count`）的结构异常全部在局部处理：放弃**整次**牌组解析、`deck=()`、写入明确原因码，三张候选照常发布。
- 明确区分字段缺失与 null：缺失 → `no_card_id_field` / `no_count_field`；null → `slot_without_card_id` / `null_count`（按上游 `if counts else []` 语义当作该槽位 0 份，并记录 `deck_note`）。
- 一致性复读不再覆盖已发布读数的诊断（复读只用于判定撕裂，诊断以第一次读取为准）。
- 只吞 `UnsupportedLayout`（结构类）；进程退出、权限不足、取消信号、底层读取错误仍向上抛出，整次读取失败。
- 牌组上限仍为 40 份，超限整体失败，不截断、不补齐。

### 4. 诊断语义

`Recovery Executed` 原来等于“merge 调用过”，没有快照时也可能显示 yes。现在拆成两个字段：

- `Merge Executed`：合并逻辑是否运行过（`[Arena Recovery]` 中可见）。
- `Recovery Executed`：是否真的建立了快照并产出历史牌（`snapshot != None and recovered > 0`）。
- 另有 `Snapshot`、`Snapshot Window`（下界 → 上界与时长）、`Snapshot Size`、`Recovered Cards`、`Pending Cards`、`Uncertain Picks`、`Deck Reason`（含 `deck_note`）。

无快照、最终牌组已确认（`exact_deck`）或牌组结构不可读时，`Recovery Executed` 均为 no，并给出原因码。实机验收时若看到 `Merge Executed: yes` 而 `Recovery Executed: no`，直接看 `Recovery Reason` 与 `Deck Reason` 即可定位，不必再猜。
